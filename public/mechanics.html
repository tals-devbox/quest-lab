How rooms and game mechanics work

Your room-and-engine model is substantially correct. A room supplies its particular places, objects, entrances and behavior. The engine supplies shared movement, interaction, inventory, conversation, timing and rendering. Room state also depends on shared world state: what you carry, what you learned, time, character skills and earlier quests.

What the original SCI game contains

PartWhat it does
Room and object scriptsEnter/leave behavior, objects and characters, allowed verbs, prerequisites, reactions, and scripted sequences. An actor, room and running sequence can each have its own state.
Shared world stateInventory, flags, quests, abilities, money and clock. A room is not an isolated state machine: progress in one room changes another.
Walk polygons / control regionsWhere the actor's feet may move; trigger regions, door approaches and scene boundaries. A clickable doorway and a walkable path to it are separate things.
Priority / occlusionWhich background pixels or foreground objects cover an actor at a given depth. This is separate from collision: a canopy can hide you while the ground beneath remains walkable.
Sprites and presentationAnimation frames, foot anchors, scale, depth, sound, message lines and camera/view type. A close-up of a notice board has no walking hero.

There is no single universal “all possible room states” table in the original. Some state machines are explicit changeState scripts; others are conditions in verb handlers or inherited shared classes. Understanding a room requires those dependencies as well as its script.

What this remake actually runs

The current Remake is based on the 1992 VGA point-and-click game. The 1989 EGA game uses typed commands, including conversation topics. The changes are broader than image quality; your decision about which edition to follow remains deferred.

  1. Original reference players: the EGA and VGA tabs run their original programs in the bundled js-dos/DOSBox interpreter, with separate saves. They do not use the remake's rules.
  2. Main Remake: Phaser renders the scene. Native TypeScript rules and structured campaign data decide gameplay. Imported source metadata supplies many objects, messages, polygons and exits. This is a reconstruction, not complete execution of the original scripts.
  3. Limited source presentation: a bounded parsed-SCI runtime supplies timed presentation in the inn, Guild and magic shop (301,311,314). Native gameplay remains authoritative. Other rooms mostly use inspected baseline staging plus native rules.
  4. Experimental source preview: a separate, incomplete SCI runtime exists locally. It can stop at unsupported operations; it is not the full original reference player and does not establish remake parity.

The imported inventory contains 100 room definitions and 1,553 extracted interaction cases; the native campaign contains 168 rules. These are different counting units, not a completion percentage. Many imported cases are not mapped or verified as equivalent gameplay. A room with a picture and exits is not a completed reconstruction.

Why the reported failures happened

Some behavior was manually adapted into the native rule set, leaving incomplete dependencies and sequences. The renderer also treated every scene as a walkable room, and applied original masks to newly painted shapes. The hero's separate shadow was not masked with the actor. Those are reconstruction defects, not missing concepts in the original game.

What changed in v0.5.2

  • Files and version: an always-visible navigation button and title-screen entry show the running app version and installed data. Game-data import and save import are separate; pack validation and atomic replacement preserve saved adventures. The download panel distinguishes the latest version from the app actually running.
  • Reversible creation: plus/minus and left/right arrows change an ability by five. Creation allocations have a refund ledger; undo returns the absent-skill surcharge. Reset restores the initial 50-point budget. Once creation finishes, later earned skills cannot be refunded.
  • Explicit view types: the notice board and the two game boards do not spawn a walking hero or shadow.
  • Art-bound geometry: town square, Guild street and Erana's Peace have authored walk areas or occluders bound to their particular paintings. The pathfinder uses those same boundaries. Replacing the art does not silently reuse its old authored mask.
  • Consistent depth: modern actors sort by their feet. The hero and its shadow use the same occlusion depth. Original priority planes apply only to matching original artwork; other paintings need their own occluders.
  • Dialog ownership: the opening speech waits for an existing file/stat dialog rather than replacing it.

Limits: only six explicit view contracts and three authored painting geometries are included in this correction. Other paintings still need visual/collision review. The tree matte uses approximate polygons, not a detailed leaf silhouette. Full source behavior, ordinary combat and all class routes remain incomplete or unverified.

What reliable prompt-driven extensions require

Prompt → room / quest / art changes → reference and geometry validation → scenario checks → rendered click-through → versioned preview → saved revision.

A new room needs its view type, art, foot anchors, walk boundaries, entrances, active objects, interactions, prerequisites and consequences, plus scenarios for its important states. Shared world state should drive both visible affordances and permitted actions. Navigation and occlusion must be reviewed against the actual painting.

The new presentation contract corrects renderer assumptions; it does not yet unify every legacy behavior path. After choosing the edition, the next architectural step is a single resolved scene description for rendering/input and one authoritative gameplay transition path, with explicit coverage for unsupported original behavior. Arbitrary extensions working perfectly in one shot are a goal to test, not something this build can guarantee.
